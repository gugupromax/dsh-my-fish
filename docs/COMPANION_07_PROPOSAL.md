# My Fish 0.7 技术方案草案

基于 0.6.6 与 DSH 0.2.2-rc.1，2026-11-10。下列设计待开发和验收。

开发版说明：猜评论、主动续聊和共同梗分别使用工作区内独立记录文件，随工作区迁移；不改变旧版 companion.json 格式。到期目标通知保留原有用途，兴趣续聊单独做证据门禁；升级前已投递的旧轮次沿用旧通知规则。真实会话互动、实际模型及定时执行仍需验收。

## 一起猜评论

复用固定主会话、BV 输入、Social 的资料和评论工具。聊天和界面共用同一套回合状态。界面走 CompanionRuntime.chat，沿用 requestId，并把玩法纳入请求指纹。现有普通 BV 提示允许直接读评论，游戏入口使用独立提示。

每个主会话最多一局进行中。CompanionStore 保存 roundId、sessionId、BV、阶段、修订号、双方猜测、用户消息 ID、读取回执与揭晓快照。companion.json 有严格字段校验，扩展读写格式时，旧文件缺少回合字段按空集合加载。

1. 用户发起后只读标题和简介，Fish 先保存并说出猜测。在用户回答前，工具入口拦住针对本局 BV 的评论读取。
2. 用户作答或明确说跳过后，才取最多五条顶层热评。回答须来自本局开始后的主会话用户消息；换话题可取消。
3. 保存实际评论 ID、短摘录、采样时间和实际条数，再生成揭晓。零条时说明样本不足。重复揭晓返回同一快照，来源文字只作材料。
4. 阶段转换串行写入，使用回合 ID 和修订号拒绝迟到请求。重启恢复已保存阶段，读取结果未知时等待明确重试。换绑后旧局留在原会话。

## 带回一条发现

复用 Scheduler 的作息、额度、暂停，以及兴趣线的 reflect、respond、来源回执和动态盒。在自主兴趣轮次写动态前，要求关联活跃话题、实际用户原话和有新内容的读取证据。模型负责表达，插件检查证据归属和话题状态，再决定写入或安静结束。

后端用话题 ID、规范来源与内容指纹生成去重键。相同资料重读会更新 readAt，不能据此认定有新发现。复用 addNotice 的 key，同时持久记录已投递指纹；同一话题只保留一条未回应发现。投递前复查暂停和免打扰。

## 重复拒绝后收尾

仅跟踪已核实的 My Fish 计划执行。按 executionId、执行会话、工具名和拒绝原因码识别重复，按调用 ID 去重。第一次永久拒绝给出报告或结束路径；同一拒绝再次出现，给本轮打上停止标记，只写一条本地提示。网络超时和零结果使用各自的处理流程。

先用实际安装版 SDK 和合成计划验证 tools/result 与 agent/pre-step 能否关联同一执行、阻止下一模型步，并让任务看板结算。单独验证过 pre-step 可以拒绝模拟轮次，完整计划结算仍待验证。验收同时检查下一次定时触发保留。

## 第二阶段与验收

共同梗只在用户明确要求记住时保存。条目包括叫法、来源原话、确认消息 ID、适用场景和最近使用时间。只在主会话按当前话题选取，支持纠正和删除。

交付顺序为宿主收尾小实验、猜评论双回合、带回发现、共同梗。先用合成数据验证取消、重复请求、重启、换绑、空评论和同内容去重；再用真实 BV 在主会话玩一局，分别核对样本真实性与聊天体验。
